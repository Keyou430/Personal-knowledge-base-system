# P0 本地企业级 RAG 知识库升级设计

## 目标

在现有本地 Python + Streamlit 知识库上完成一轮可落地的 P0 升级，使本地文档具备：

- 可追溯的文档档案、版本和来源信息；
- 保留标题、表格、FAQ 语义的结构化切片；
- 语义检索与关键词检索并行的混合召回；
- 低相关时拒答，不让模型根据不足资料猜测；
- 结论、依据、引用三段式回答；
- 手动上传后的版本替换、索引更新和检索自检；
- 旧资料显式迁移和索引重建。

本期保持本地单用户运行方式，不引入 RAGFlow、Docker、独立后端、多租户账号或外部采集服务。

## 范围

### 本期包含

1. 将现有领域作为本地知识库边界。
2. 为每个上传文件建立文档档案，记录唯一 ID、内容哈希、分类、责任人、版本、更新时间和来源。
3. 支持文档重新上传时的内容去重和版本替换；旧版本保留历史但不再参与默认召回。
4. DOCX/Markdown 按标题层级切分并保留父标题；表格保持完整；FAQ 按一问一答切分；超长内容按段落继续切分。
5. PDF 保留页码信息；其他格式至少保留文件名和文档 ID。
6. 使用 SQLite FTS5 保存可检索文本和元数据，使用现有 Chroma 保存语义向量。
7. 实现混合检索、结果合并去重、规则排序和最低相关度过滤。
8. 统一回答提示词和引用格式，资料不足时返回明确拒答。
9. 提供手动“迁移现有资料/重建知识索引”操作。
10. 保留现有经验沉淀、人工审核、去重、版本和归档能力。

### 本期不包含

- 多用户、权限和多租户隔离；
- 飞书文档、群聊、网页或录音自动采集；
- 定时任务和后台无人值守更新；
- Rerank 模型、双模型复核和自动模型路由；
- 问答反馈回流和评测集管理；
- RAGFlow、Docker 或独立 API 服务部署；
- 跨领域自动合并。

## 设计原则

- SQLite 中的文档档案和状态是事实来源，Chroma 与 FTS5 是可重建的检索投影。
- 原始文件不因迁移或重建被删除。
- 索引失败不回滚已经保存的文档档案；记录待重建状态并允许稍后重试。
- 所有更新由用户上传或点击操作触发，启动时不做全量扫描。
- 引用必须来自实际召回片段，回答不能超出召回内容。
- UI 只负责交互和状态展示，入库、迁移、检索和回答规则由服务模块负责。

## 架构

```text
Streamlit UI
   |
   +--> 文档入库服务 --> 文档加载器 --> 结构化切片器
   |                           |
   |                           +--> SQLite 文档档案 / FTS5
   |                           +--> Chroma 语义索引
   |
   +--> 混合检索服务 --> FTS5 关键词召回
   |                   --> Chroma 语义召回
   |                   --> 合并、排序、阈值过滤
   |
   +--> 回答生成服务 --> 结论 / 依据 / 引用
   |
   +--> 经验沉淀服务（现有能力，保持独立）
```

### 模块职责

- `app.py`：渲染上传、迁移、问答和检索结果；不直接操作 SQLite、Chroma 或拼装复杂提示词。
- `core/document_store.py`：文档档案、版本、状态、内容哈希、FTS5 表和迁移状态。
- `core/ingestion.py`：编排保存原文件、加载、切片、写入档案和更新两路索引。
- `core/loader.py`：保留格式加载入口，补充结构化元数据；DOCX 需读取段落和表格。
- `core/splitter.py`：按文档结构切片，统一写入 `document_id`、`document_version`、`section_title`、`page`、`chunk_index` 等元数据。
- `core/retriever.py`：保留 Chroma 语义索引能力，新增稳定 chunk ID、文档版本过滤和旧版本删除/失效处理。
- `core/hybrid_retriever.py`：执行 FTS5 和 Chroma 双路召回，融合结果并应用业务排序规则。
- `core/generator.py`：按统一回答契约生成流式或非流式回答。
- `core/migration.py`：扫描现有 `data/raw`，建立文档档案并重建 FTS5/Chroma 投影。
- `core/domains.py`：继续承载领域目录和原始文件列表等轻量文件系统操作。

## 数据模型

### `documents`

- `id`：稳定的文档 ID。
- `domain`：所属领域。
- `name`：原始文件名。
- `category`：制度、方案、手册、记录、经验或其他分类。
- `owner`：责任部门或责任人，可为空。
- `version`：文档版本号；未提供版本时由系统按内容变更递增。
- `content_hash`：规范化正文的 SHA-256。
- `source`：上传、迁移或其他来源标记。
- `updated_at`：文档更新时间。
- `status`：`active`、`superseded`、`failed`。
- `index_pending`：两路索引是否待重建。

### `document_chunks`

- `id`：稳定的切片 ID。
- `document_id`、`document_version`：所属文档和版本。
- `content`：切片正文。
- `section_title`：当前章节及父级标题上下文。
- `page`：页码，适用于 PDF 或其他可定位格式。
- `chunk_index`、`total_chunks`：切片顺序信息。
- `metadata_json`：格式特有的附加元数据。

### FTS5 投影

FTS5 以切片为检索单位，索引正文、文件名、章节标题和分类。FTS5 结果通过切片 ID 回查 `document_chunks` 和 `documents`，强制过滤非 `active` 版本。

## 文档处理与版本更新

### 新文件入库

1. 校验领域、扩展名和文件名。
2. 计算文件内容哈希，写入领域原始目录。
3. 加载为带基础元数据的 `Document` 列表。
4. 按格式执行结构化切片。
5. 在 SQLite 事务中创建或更新文档档案和切片。
6. 将新的切片写入 FTS5 和 Chroma；旧版本标记为 `superseded`。
7. 删除旧版本对应的向量投影，避免旧内容继续召回。
8. 执行最小检索自检：使用文档标题或首个有效章节查询，确认新版本可被召回。
9. 自检失败时保留文档档案，标记 `index_pending` 并显示可重建提示。

### 重复与版本规则

- 同一领域内内容哈希相同的文件视为重复，不创建新的有效版本。
- 同名但内容变化的文件视为新版本；旧版本继续保留原始文件和历史记录，但不参与默认检索。
- 用户显式指定版本号时优先使用用户值；未指定时沿用旧版本号并递增末段。
- 入库失败不覆盖现有有效版本，失败记录单独保留。

## 结构化切片策略

- DOCX：读取段落样式、标题层级和表格；表格整体作为一个切片，不拆分单元格行。
- Markdown：依据 ATX/Setext 标题和段落边界切分，切片开头带完整父标题路径。
- FAQ：识别“问题/答案”或问号边界，每组问答尽量独立成片。
- PDF：保持现有页级来源，页内按标题、段落和句子切片并保留 `page`。
- PPT/TXT/图片：保留现有提取能力，使用标题或自然段作为优先边界。
- 单片默认目标约 800 字，最大约 1000 字；超过上限按段落再切，重叠仅用于连续正文，不跨越表格或 FAQ 边界。

## 混合检索

1. 对用户问题执行 FTS5 关键词召回和 Chroma 语义召回。
2. 两路结果按切片 ID 合并去重。
3. 对包含数字、编号、日期、版本号或精确名称的查询，提高 FTS5 命中权重。
4. 对制度类查询，提高最新 `updated_at` 版本权重。
5. 使用归一化分数进行加权排序，返回 Top 5~10。
6. 过滤低于最低相关度阈值的结果；两路均无可靠结果时返回空结果。
7. 记录 query、召回切片、最终采用切片和版本信息，不记录 API Key。

P0 不引入额外 Rerank 模型；融合规则必须可测试、可解释，并保留后续接入 Rerank 的接口。

## 回答契约

系统提示词固定要求：

1. 先给简明结论；
2. 再给出基于召回资料的依据；
3. 最后列出引用来源。

每个引用至少包含文档名称、版本、章节或页码、片段摘要。模型只能使用注入上下文中的事实。若检索结果为空或低于阈值，系统直接返回“知识库暂无相关内容，请补充或更新相关文档”，不调用模型生成猜测。

## 迁移与重建

- 新增独立的“迁移现有资料/重建知识索引”操作。
- 操作扫描 `data/raw/{domain}` 中的受支持文件，为每个文件生成文档档案、切片和两路索引。
- 迁移不删除原始文件，不覆盖已有有效档案；相同哈希直接复用。
- 迁移按文件逐项提交，单文件失败不阻断其他文件。
- 重建可清空并重新生成 FTS5 和 Chroma 投影，但不删除 SQLite 文档档案和原始文件。
- 重建完成后显示成功、失败和待重试文件清单。

## 错误处理

- 文件解析失败：显示文件名和可理解的失败原因，保留现有有效版本。
- SQLite 事务失败：回滚档案和切片变更，不产生半条文档记录。
- Chroma 或 FTS5 投影失败：档案保存成功，标记 `index_pending`，允许单独重建。
- API Key 未配置或模型调用失败：保留问答和引用状态，显示配置或重试提示。
- 重复点击上传/重建：通过内容哈希、文档 ID 和操作状态实现幂等。
- 迁移遇到旧格式或损坏文件：跳过该文件并继续处理其他文件。

## 测试与验收

### 自动化测试

- DOCX 标题、表格和 FAQ 的结构化加载与切片。
- PDF 页码和切片元数据保留。
- 文档内容哈希、重复上传和版本替换。
- SQLite 文档档案、FTS5 建立、查询和版本过滤。
- Chroma 切片稳定 ID、旧版本删除和新版本写入。
- 混合检索融合、关键词优先规则、低相关阈值和空结果。
- 回答上下文包含版本/章节/页码引用，空检索时不调用模型。
- 迁移成功、单文件失败、投影失败和可重建状态。
- 现有经验库和 Streamlit 启动测试继续通过。

### 验收标准

1. 上传一个含标题和表格的 DOCX 后，问答能命中对应章节或表格，并显示准确来源。
2. 查询编号、日期或制度名称时，关键词命中能够优先返回正确切片。
3. 重新上传同名修改文件后，默认只召回新版本，历史仍可查看。
4. 无相关资料时，系统拒答且不让模型编造答案。
5. 任一路索引失败时，文档档案不丢失，并能通过重建恢复。
6. 对现有 `data/raw` 执行迁移后，原有资料可检索且原始文件未被删除。
7. 现有文档浏览、领域管理、问答和经验沉淀功能继续可用。
8. 应用启动不自动加载 Embedding、Chroma 或执行全量迁移。

## 交付顺序

1. 文档档案与 SQLite/FTS5 基础层。
2. 结构化加载与切片。
3. 版本化入库和 Chroma 稳定索引。
4. 混合检索与低相关过滤。
5. 回答契约和引用展示。
6. 迁移/重建 UI 与错误处理。
7. 全量测试、编译检查、依赖检查、差异检查和本地 Streamlit 验证。
