# 本地目录增量同步设计

## 目标

为单用户本地可持续版增加一个确定、可预览、可审计的目录同步入口。用户可扫描一个本地资料目录，先查看新增、变更、未变化、恢复、缺失、不支持和解析失败项，再显式应用。同步不会因源文件临时缺失而删除知识库，也不会引入后台 worker、外部连接器、认证或多租户能力。

本设计落实 ADR-0002、ADR-0003、ADR-0004、ADR-0005 和 ADR-0008。

## 范围

### 本期包含

- 递归扫描一个明确指定的本地目录，按相对路径建立稳定来源身份；
- 使用原始文件 SHA-256、文件大小和修改时间识别未变化项，未变化文件不重新解析；
- 默认 dry-run，仅显式 `--apply` 写入；
- 新增、变更、未变化、恢复、缺失、不支持、无效和应用失败等逐文件结果；
- 源文件缺失时保留档案与历史版本，将当前文档标记为来源缺失并从默认检索排除；
- 同一路径内容变化时生成新版本；路径改名按“新来源 + 原来源缺失”处理；
- SQLite/FTS5 先写入，语义索引失败则标记待重建，由用户点击现有“重建知识索引”；
- 单运行锁、逐文件失败隔离、安全 JSON 报告和 JSONL 运行日志；
- CLI、Windows Task Scheduler 示例、回归测试和验收门禁覆盖。

### 本期不包含

- 常驻文件监听或后台重建任务；
- 飞书、群聊、网页、录音等外部连接器；
- 自动物理删除档案、历史版本、切片或备份；
- 自动推断文件改名并合并历史；
- 身份认证、角色、权限过滤或多租户；
- 自动修改检索权重、切片参数或模型配置。

## 方案选择

### 方案 A：SQLite 同步清单 + 文档来源存在状态（采用）

同步清单与文档档案位于同一 SQLite 数据库，记录来源根目录哈希、领域、相对路径、文件指纹、关联文档和 present/missing 状态。文档表增加 `source_present`，关键词和语义结果都以此过滤。

优点是事务边界清楚、备份会自然包含同步状态、缺失来源可审计，且不需要保存完整源目录到报告或日志。代价是需要一次向后兼容的 SQLite additive migration。

### 方案 B：独立 JSON manifest

实现较短，但清单与 SQLite 档案可能在崩溃或恢复后不一致，并发写入和历史审计也更脆弱，不采用。

### 方案 C：只扩展文档 status

无法清楚表达来源路径与文档版本的关系，也无法安全处理同内容不同路径、恢复和未来多来源，不采用。

## 数据模型

### documents 扩展

为现有 `documents` 表增加：

```text
source_present INTEGER NOT NULL DEFAULT 1
```

初始化时通过 `PRAGMA table_info` 检查并执行幂等 `ALTER TABLE`，已有数据库全部视为来源存在。`active/superseded/failed` 继续表达文档生命周期，`source_present` 单独表达当前来源是否可用。

默认关键词检索、FTS 重建、语义结果融合都要求文档 `status='active' AND source_present=1`。文档浏览仍显示来源缺失项，便于恢复或清理。

### directory_sync_sources

新增同步清单表：

| 字段 | 含义 |
|---|---|
| `root_key` | 规范化绝对源目录的 SHA-256，不保存根目录原文 |
| `domain` | 当前本地知识领域 |
| `relative_path` | 使用 `/` 的源目录相对路径 |
| `document_id` | 当前关联的文档档案 ID，可空 |
| `file_sha256` | 原始文件字节 SHA-256 |
| `size` | 文件大小 |
| `modified_ns` | 纳秒修改时间，仅作快速比较证据 |
| `state` | `present` 或 `missing` |
| `last_seen_at` | 最近一次扫描观察时间 |
| `last_applied_at` | 最近一次成功应用时间 |

`(root_key, domain, relative_path)` 唯一。表内不保存文件正文、API Key 或完整根目录。

## 扫描与预览

1. 校验源目录存在、领域非空、数据库和输出位置可用。
2. 取得单运行锁。锁文件使用原子创建；已存在时返回配置/运行冲突，不启动第二个扫描。
3. 递归枚举普通文件，不跟随符号链接。所有相对路径必须保持在源目录内。
4. 不支持的扩展名报告为 `unsupported`，不写入清单。
5. 对清单中相同路径且 SHA-256、大小一致的文件报告 `unchanged`，不解析正文。
6. 新路径或指纹变化的文件执行现有解析与切片预检：成功后报告 `new` 或 `changed`，失败报告 `invalid`。
7. 清单为 missing、当前重新出现且指纹未变化的文件报告 `restored`，无需重新解析。
8. 清单中 present、但本轮未观察到的路径报告 `missing`。
9. dry-run 到此结束，不修改文档表、同步清单、FTS 或 Chroma。

预览项包含相对路径、动作、安全原因码、文件 SHA-256、大小、修改时间、内容哈希、关联文档 ID和拟用版本。对外文本/JSON 不包含正文或完整源目录。

## 显式应用

`--apply` 在同一个锁和同一次预览快照中逐项处理：

- `new`：以相对路径作为文档名称和归档相对路径入库，建立 present 清单记录；
- `changed`：重新核对 SHA-256，内容未在预览后变化才创建新版本，并把清单指向新文档；
- `unchanged`：只更新清单的最近观察时间；
- `restored`：恢复清单 present 状态和关联文档 `source_present=1`；
- `missing`：将清单标记 missing，并重新计算关联文档的来源存在状态；不删除任何资料；
- `unsupported` / `invalid`：不写入，保留在报告中；
- 应用阶段单文件异常：记录安全原因码并继续后续文件。

目录同步允许同内容的不同相对路径形成独立档案，保证改名仍表现为新来源与旧来源缺失。现有批量上传继续保持原有跨文件内容去重语义。

入库使用现有 `ingest_file`，增加向后兼容的可选参数：显式文档名、归档相对路径和是否跨名称去重。默认值保持现有上传、迁移和测试行为；目录同步关闭跨名称去重。

## 语义索引与缺失过滤

apply 仅在存在 `new` 或 `changed` 项时尝试加载当前领域向量库。加载或写入失败不回滚 SQLite 档案和 FTS5，而是设置 `index_pending=1`。不创建后台任务；用户通过现有页面按钮重建。

缺失来源的向量可暂时留在 Chroma 中，但 `HybridRetriever` 在融合语义结果前读取 SQLite 文档档案，仅允许 active 且 source_present 的结果进入回答。这样缺失标记立即生效，且恢复时无需强制重建向量。

## CLI

```powershell
python -m core.directory_sync `
  --source D:\KnowledgeSource `
  --domain 默认
```

默认输出预览。显式应用：

```powershell
python -m core.directory_sync `
  --source D:\KnowledgeSource `
  --domain 默认 `
  --apply `
  --json-out data/sync/latest.json
```

可选参数：`--database`、`--log-file`、`--lock-file`。默认数据库使用 `DOCUMENT_DB_PATH`，日志写入 `data/logs/directory-sync.jsonl`，锁写入 `data/directory-sync.lock`。

退出码：

| 退出码 | 含义 |
|---:|---|
| 0 | 扫描/应用完成，无解析或应用失败 |
| 1 | 存在解析失败、快照变化或逐文件应用失败 |
| 2 | 参数、源目录、数据库或运行锁配置错误 |
| 3 | 未捕获异常 |

`missing` 和 `unsupported` 是需关注的扫描结果，但本身不产生非零退出码；`invalid` 和 apply failure 返回 1。

## 结构化证据与隐私

每次运行生成一个随机 `run_id`。JSON 报告包含模式、领域、开始/结束时间、聚合数量、相对路径、动作、原因码、待重建和重试清单。JSONL 日志记录一条 run summary 和逐文件结果。

报告与日志禁止包含：文件正文、切片内容、完整绝对源目录、环境变量、API Key、模型响应和 Python traceback。异常映射到稳定原因码；终端仅显示相对路径和安全摘要。

## UI 与运维

- 文档健康摘要增加“来源缺失”数量，整体状态为 attention；
- 文档列表把来源缺失显示为“源文件缺失”，优先于“当前生效”，但保留“待重建索引”提示；
- 不新增后台页面或 worker；同步入口本期以 CLI 为主；
- 使用指南提供 Windows Task Scheduler 示例，任务命令必须显式包含 `--apply`；
- 同步锁阻止 Streamlit 外部的两个 CLI 同时修改同一档案。现有上传并发模型不在本期扩展。

## 测试策略

新增聚焦测试覆盖：

1. 新目录 dry-run 不写数据库；
2. apply 新文件后生成档案、FTS 和同步清单；
3. 第二次扫描为 unchanged，不创建新版本也不重新解析；
4. 同路径变更创建新版本，旧版 superseded；
5. 文件缺失只标记，不删除；关键词和语义融合均不召回；
6. 文件恢复后重新进入检索；
7. 改名同内容生成新档案，旧来源标记 missing；
8. 不支持格式、解析失败和单文件写入失败不会阻塞其他文件；
9. 文件在预览后变化时 apply 拒绝该项；
10. 锁冲突返回退出码 2；
11. JSON/JSONL 不包含完整根目录、正文或密钥；
12. 已有 SQLite 数据库自动增加字段，现有上传/迁移去重语义不变；
13. 全量 `pytest`、`compileall`、`git diff --check` 和 P1 acceptance gate 通过。

## 验收标准

- 同一个源目录连续执行 apply，第二次不新增版本；
- 修改、删除、恢复和改名四种生命周期均有稳定报告和测试证据；
- dry-run 对文档、切片、FTS、同步清单和向量索引零写入；
- 任一源文件缺失后，默认问答无法通过关键词或语义路径召回该档案；
- Embedding 不可用时文档仍可通过 FTS 检索，并显示待重建；
- 任何扫描/应用错误均不会泄露正文、完整源目录或密钥；
- 不新增外部连接器、后台 worker、权限系统或多租户代码。
